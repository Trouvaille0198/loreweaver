# 模组从哪里来，又怎样变成一场游戏

*给想弄明白整条链路的玩家、守秘人与模组作者。只想马上进桌，可以先读[玩家上手](play.zh.md)；想动手制作，接着读[模组创作教程](authoring.zh.md)。*

“导入模组”听起来像把一个文件打开，实际上至少包含四件事：把内容装到服务器、选择哪份世界进入房间、把资料投进守秘人的上下文，以及在每个回合里让规则和状态真正运转。把这四层分开看，很多操作和故障都会清楚得多。

---

## 1. 所谓“模组”是什么

在 Loreweaver 里，**模组是一次冒险的可执行内容**：不只有故事正文，还可以声明规则、秘密、演员、状态、界面和回合行为。它给守秘人一个要主持的世界，也给确定性引擎一套要维护的账。

仓库里有三种容易混在一起的载体：

| 载体 | 它是什么 | 进入房间后得到什么 |
|---|---|---|
| 原始剧本文档 | `.txt`、`.md`、`.pdf`、`.doc` / `.docx` 等正文 | 一份经过分析的守秘人知识池和玩家级知识投影 |
| 世界卡 | 原生 `*.lorecard.json`，或带世界机制的酒馆 JSON / PNG | 世界书、变量、钩子、预设角色、演员、规则系统等结构化内容 |
| 内容包 | 一个带 `pack.yaml` 的 `.lwpack` | 用于安装和分发的容器；里面可以装世界卡，也可以只装规则、技能、界面或素材 |

因此，**`.lwpack` 不天然等于一个模组**。它可以装一个完整冒险、多个可选择的冒险，也可以只是一个扩展包。反过来，一份纯文本剧本不用打包，也能经 `.module` 进入房间。

### 一个完整内容包可以包含什么

```text
harbour-bell/
  pack.yaml                    包的身份、版本、作者、许可和内容清单
  cards/*.lorecard.json        世界卡、人物卡
  rulepacks/*.yaml             规则系统或对基础系统的补丁
  lorebooks/*                  独立世界书
  skills/<id>/SKILL.md         守秘人的主持方法和工具约束
  skills/<id>/hooks.js         沙箱中的回合生命周期行为
  ui/panels.yaml               变量面板、侧栏、弹窗
  ui/presentation.yaml         幕卡、信件、剪报、地图钉等演出资料
  presets/*                    提示风格预设
  prep/*                       由守秘人在准备阶段执行的脚本
  assets/*                     图片、音频和其它素材
```

不是每个模组都需要全部目录。最小的原生模组可以只有 `pack.yaml` 和一张世界卡；只需要故事知识时，一份原始剧本文档也够用。

## 2. 从文件到房间：导入发生了什么

先分清“安装”和“进入房间”：

```text
作者目录 ──打包──> .lwpack ──安装──> 服务器数据目录
                                          │
                     守秘人在房间里选择和启用
                                          ▼
                               房间内容、规则、界面与状态
                                          │
                                  玩家正常发言
                                          ▼
                                回合组装、结算与叙事
```

### 路线 A：导入一份原始剧本文档

守秘人执行：

```text
.module <文件>
```

服务端会：

1. 读取文本，或从 PDF / Word 中抽取正文；
2. 分块并建立检索索引；
3. 用一次独立的模组分析调用识别场景、NPC、线索、秘密、节奏和规则提示；
4. 建立两份知识投影：守秘人池保留谜底，玩家池按分析结果排除守秘人秘密；
5. 把初始化状态标为可游玩；分析失败时使用确定性的降级摘要，并明确标记为 fallback。

分析期间，房间会阻止玩家把普通行动塞进半成品上下文。完成后，模组池会进入守秘人每回合的固定提示段；向量分块只在需要检索时补充相关原文。

这条路适合已经写好的普通剧本。它**不会凭空生成**类型化变量、钩子、面板、预设角色或规则包；正文里写着“警觉值 0–5”仍然只是文字，除非作者把它声明成结构化追踪器。

### 路线 B：安装并启用一个内容包

在服务器终端安装：

```bash
uv run python -m app --install <本地路径|https://链接|GitHub仓库/目录/文件链接|gh:owner/repo[@tag]>
```

这会验证清单、哈希和信任信息，然后把内容写入服务器数据目录。它不会替任何房间作选择。

守秘人在远程房间中也可以执行：

```text
.pack install <本地路径|https://链接|GitHub仓库/目录/文件链接|gh:owner/repo[@tag]>
```

这条房间命令会先安装包。若包里恰好有一张世界卡，它会把那张卡及其同源世界书、面板、演出资料和 KP 技能作为房间模组一起启用；若有多张世界卡，回执只列出选择命令，不在选择前启用任何模组专属开关。没有世界卡的扩展包不占用房间的模组名额，并会启用它实际声明的 KP 技能与界面。

包内各类内容的激活方式并不完全相同：

| 内容 | 只执行服务器 `--install` | 房间 `.pack install` | 手动入口 |
|---|---:|---:|---|
| 世界卡 | 安装 | 唯一一张时导入；多张时等待选择 | `.import <包/卡> world` |
| 人物卡 | 安装 | 不认领 | 玩家 `.import <包/卡> pc` |
| 规则包 | 安装并可发现 | 可被世界卡选中 | 由世界卡 / 建卡命令选择 |
| KP 技能 | 安装并可发现 | 唯一世界卡或扩展包时启用；多卡时等待选择 | `.skill enable <id>` |
| 面板与演出资料 | 安装并可发现 | 唯一世界卡或扩展包时启用；多卡时等待选择 | `.panels enable <包 id>` |
| 独立世界书 | 安装 | 唯一世界卡时作为同源模组资料导入；否则不导入 | `.lore import <包/路径>` |
| 提示预设 | 安装 | 不启用 | `.preset import …` 后 `.preset enable <id>` |
| 准备脚本 | 安装 | 不执行 | 守秘人在准备阶段明确执行 |
| 素材 | 安装并按哈希提供 | 随引用使用 | 由卡、面板、钩子或导演引用 |

这个矩阵比“包已经装好了”更值得相信。每种可执行内容都有自己的房间级开关，避免磁盘上的内容悄悄改变一桌正在进行的游戏。

### 路线 C：把一张世界卡导入房间

守秘人执行：

```text
.import <文件或包内引用> [规则系统] world
```

玩家不能走 `world` 路径。人物卡的世界机制会在玩家导入路径中被结构性剥离；改变整张桌子的脚本、变量和秘密只能由守秘人放行。

一次世界卡导入会依次处理：

1. 解析卡格式，区分人物内容与世界机制；
2. 解析显式规则、包声明的角色系统和房间默认系统；
3. 导入世界书和酒馆兼容的 InitVar / MVU 变量树；
4. 安装房间钩子与 EJS 模板能力；
5. 写入模组身份与守秘人专属 brief；
6. 定义类型化变量；
7. 创建预设角色和卡内演员；
8. 固定房间规则系统，并启用同包的 KP 技能、面板、演出资料与独立世界书。

整个过程是一次原子替换：每个房间只能有一个模组，纯文本模组与世界卡互斥；任何一步失败都会恢复导入前的当前模组和房间开关。导入回执只是准备完成的信号，不是开场旁白。确认角色、规则和面板后，玩家发出的下一条普通行动才进入正常回合。

### 路线 D：创作时实时挂载

作者可以在开启开发源目录后执行：

```text
.dev mount <源目录>
```

房间会在保存后重载源目录中的卡、世界书和界面，适合边写边测。它是创作沙箱，不是分发方式；玩家实际拿到的仍应是经过构建和校验的 `.lwpack`。

## 3. 房间因为模组多了什么

模组导入后，房间拥有的不是一段塞进聊天记录的长文本，而是两组东西。

### 作者带进来的静态内容

- **守秘人知识**：谜底、幕后动机、场景结构、线索关系和主持说明；
- **世界书**：按关键词、条件、概率、优先级、延迟、冷却和 sticky 状态取用的设定条目；
- **规则包**：检定公式、成功等级、卡表形状、衍生属性、资源和命令；
- **类型化变量**：有类型、边界、枚举和值可见性的追踪器；
- **MVU 变量树**：酒馆生态的层级变量，默认不向玩家公开；
- **预设角色与演员**：可认领角色、NPC / 同伴记录及其卡表；
- **KP 技能**：守秘人的主持程序、风格和可用工具约束；
- **钩子与模板**：在回合事件上响应、更新状态、发区块或渲染内容；
- **面板、演出资料和素材**：把状态与线索变成客户端可展示的东西。

### 游玩过程中长出来的房间数据

- 玩家角色的认领、卡表和资源变化；
- 游戏时钟、场景、战斗轮次、关系轨和模组变量；
- 书记官根据已经发生的叙事提出并经引擎校验的记账结果；
- 每回合的编年史、战役摘要、未结线程和可检索记忆；
- 这桌人的长期习惯；
- 叙事日志、媒体事件、面板状态和战报。

后一组属于**这个房间的战役**，不是作者包里的静态素材。备份房间时要带走它们；把同一个包导入另一间房，不会复制这桌已经发生的故事。

### 谁能看到什么

守秘人拿完整模组真相，因为主持者必须知道谜底。玩家、NPC、同伴和演出导演拿各自的投影：守秘人专属世界书、NPC 秘密、守秘人变量和未公开 MVU 叶子不会出现在玩家级传输中。

这不等于主守秘人模型在行为上绝不会说漏嘴。结构负责不把无权资料交给玩家级参与者；主守秘人看过秘密以后是否克制，由提示约束和真实模型评测监督。

## 4. 模组在一个回合里怎样被游玩

玩家不需要“启动剧本”。他只需说明角色做什么。一个普通回合大致是：

```text
玩家意图
  │
  ├─ 引擎取得角色、房间状态、相关世界书和战役记忆
  ├─ 唯一的 Keeper 组装器拼出本回合上下文
  ├─ Keeper 选择叙事或调用工具
  │    ├─ 检定：引擎先掷真骰并算成功等级
  │    ├─ 状态：引擎校验类型、边界、权限和规则
  │    └─ NPC：独立演员只拿自己的记录与知识
  ├─ 回复流式进入故事日志
  ├─ Scribe 对照叙事补记客观事实与编年史
  └─ 若形成剧情节拍，Director 用玩家投影生成演出事件
```

### 守秘人每回合实际拿到哪些模组资料

固定头部放规则系统专长、交互风格、原始剧本知识池、启用的提示预设、KP 技能和战役摘要。变化尾部放与当前语境匹配的世界书、游戏状态、关系、变量、MVU、钩子注入、近期线程与召回记录。

世界书不会把全部正文每次都塞进去。引擎根据最近对话和状态匹配条目，并受条数与字符预算约束；`constant` 条目常驻，关键词 / 条件条目按需出现。这让模组可以比一次模型上下文大得多，也避免无关设定淹没当前场景。

### 各类数据在游玩时的作用

| 数据 | 谁消费 | 在桌上造成什么结果 |
|---|---|---|
| 场景、线索、秘密 | Keeper 提示与检索 | 决定叙事知道什么、该铺什么线索；秘密不直接给玩家 |
| 规则包 | 确定性引擎 | 决定掷什么骰、成功档位、卡表和写入是否合法 |
| 世界书触发条件 | 世界书引擎 | 只在相关话题、状态或时机把条目送进 Keeper 上下文 |
| 类型化变量 | 引擎、Keeper、面板 | 跟踪警觉、日期、进度等；越界写入会被拒绝或夹紧 |
| MVU 变量树 | 钩子、EJS、Keeper、面板 | 兼容层级状态；守秘人用 `.var expose` 公开玩家可见分支 |
| 预设角色 | 角色与卡表系统 | 玩家排他认领，释放后恢复模组原始卡表 |
| NPC / 同伴记录 | 独立演员 | 限定该演员的人设、秘密、已知信息和数值能力 |
| KP 技能 | Keeper 提示与工具过滤 | 告诉 Keeper 怎样主持，并可解锁模组工具或钩子 |
| 钩子 | 沙箱运行时 | 响应回合、检定、变量变化等事件，发声明式效果 |
| 面板 | 服务端投影与客户端 | 把允许公开的状态画成进度条、列表、侧栏或弹窗 |
| 演出资料 | Director | 在剧情节拍生成幕卡、信件、剪报、地图钉、图像或音频提示 |
| 资产 | 客户端媒体通道 | 显示手作物、地图、立绘，播放 BGM / ambience / SFX |
| 编年史与摘要 | 记忆折叠、`.recap` | 让长团跨过上下文窗口；玩家回顾不含守秘人批注 |

这里有一条最重要的边界：**模型负责叙事，代码负责事实。** 骰子、成功等级、卡表、变量边界、权限、投影与随机表不能由模型随口决定。

## 5. 开桌前怎样检查

对结构化模组，守秘人可以按下面的顺序检查，而不是看到“导入成功”就直接开场：

```text
.import list                 查看已安装包里的卡
.pack install <ref>         安装并启用一个包
.pc                         确认预设角色池
.skill status               确认主持技能
.panels                     确认模组界面
.var list                   确认追踪器和未公开变量
.phase                      确认 Keeper 工具处于 prep 还是 play
```

成功导入纯文本模组或世界卡后，自动工具阶段会进入 `play`。只有守秘人明确用 `.phase` 固定阶段时，手工选择才覆盖自动判断。

还应确认：

- 世界卡选中的规则系统与角色卡一致；
- 应给玩家看的 MVU 分支已经 `.var expose <前缀>`，秘密分支仍隐藏；
- 包需要的面板和 KP 技能确实启用；
- 提示预设与准备脚本按回执说明明确启用或执行；
- 同模组世界书已经导入，额外资料按作者说明处理；
- 玩家已经认领预设角色或创建了合法角色；
- 重要战役先做备份，再开始第一次真实模型回合。

### 切换到另一份模组

独立战役通常适合使用独立房间。同一房间里的日志、玩家角色、编年史、习惯和手工配置属于长期战役状态，不归模组导入所有。

在同一房间导入另一份纯文本模组或世界卡时，导入事务会完整替换当前模组拥有的世界书、知识池、brief、钩子、变量架构、MVU 树、预设角色、模组 NPC、模块向量，以及由该模组启用的技能和界面。手工启用的通用技能、非模组资料、玩家角色和战役记录不受影响。重要战役仍应先备份；导入失败时房间保持导入前状态。

### 预设角色的来源与清理

预设角色池里的每个角色都带一个来源标记，"预设角色"卡片显示的是房间里现有的全部角色，不只是当前模组带来的：

- **模组自带**（来源指向模组包）：导入时从包里复制进房间。换模组时随旧模组一起清掉；重新导入模组会把缺的角色补回来（已有的不重复）。
- **房间自建**（`.pc gen` 或 AI 主持人生成）：属于这张桌子自己的资产。换模组时**刻意保留**，也不随 `.reset` / `.reset chars` 清除——只有 `.reset all` 连房间一起抹掉时才会消失。

因此旧冒险里为当时的剧情临时生成的自建角色，换模组后会继续留在预设角色列表里。清理它们用 `.pc delete <名字>`——该命令只接受**房间自建且无人认领**的角色，模组自带的预设删不掉，只能靠换模组或重新导入来替换。

## 6. 玩家怎样玩，怎样玩得更好

### 最简单的玩法

用自然语言说清三件事：**你想做什么、怎么做、愿意承担什么风险**。

> 我贴着仓库外墙绕到后窗，先听里面有没有人；如果没有动静，我就用铁丝试锁，但不想惊动码头守卫。

这比“我调查”更容易让守秘人找到相关场景资料、选择合适技能，也给失败留下有意义的后果。

### 值得掌握的指令

| 目的 | 指令 |
|---|---|
| 看或认领模组角色 | `.pc`、`.pc claim <名字>` |
| 自己掷骰 | `.r <表达式>` |
| 用卡上技能检定 | `.ra <技能>` |
| 看 / 改允许修改的卡表 | `.st`、`.st <项目>=<值>` |
| 查看模组文字面板 | `.panel <id>` |
| 看无剧透前情 | `.recap` |
| 导出本场战报 | `.report` |
| 查看这一桌全部可用命令 | `.help` |

### 六条实用技巧

1. **把角色知道的和玩家猜到的分开。** 看见一个可疑面板值，不代表角色知道幕后原因。
2. **先描述方法，再等检定。** 不确定行动由 Keeper 选择是否需要骰；主动 `.ra` 适合规则和目标都很清楚的时刻。
3. **失败后换方法，不要原地重掷。** 失败应该改变处境、代价或路线；利用这个变化继续推进。
4. **检查手作物和面板。** 图片、信件、地图钉和进度条可能就是线索，不只是装饰。
5. **让同伴各自行动。** NPC 和 AI 同伴没有守秘人全知视角；问对人、分享信息本身就是玩法。
6. **长团先看 `.recap`。** 中途加入或隔周继续时，先从玩家投影的摘要恢复共同事实，少靠聊天记忆猜。

如果规则数字、面板与叙事冲突，指出具体一项让守秘人核对。叙事说“已经第三天”而追踪器仍是第一天，属于值得记录的问题，不应让模型用更多台词把它糊过去。

## 7. 信任、隐私与失败边界

- `.lwpack` 安装前会验证清单与内容哈希，并披露脚本、EJS、素材和可能的图像生成开销；它仍然是你选择运行的第三方内容。
- 钩子和 EJS 在 QuickJS 沙箱中运行，但它们可以在声明的能力内改变房间状态和输出。
- 远程大模型会收到它负责的提示内容。主 Keeper 的提示按设计包含守秘人秘密；要求资料完全不离开本机时，应使用本地模型后端。
- 玩家级参与者只收到文档投影。玩家导入人物卡时，世界脚本、变量架构和 EJS 会被剥掉。
- 导入、分析或安装失败时，不应继续靠猜测游玩。查看回执，确认房间规则、变量、技能、面板和当前模组，再决定重试、恢复备份或换房间。

## 8. 实现契约与回归保护

模组入口共同遵守以下契约；这些也是维护模组导入代码时需要保住的边界：

| # | 契约 | 可观察结果 |
|---:|---|---|
| 1 | 每个房间只能有一个模组，纯文本模组与世界卡互斥。 | Keeper 不会同时收到两份模组的提示资料。 |
| 2 | 每项模组内容都带稳定来源，替换按来源清理。 | 钩子、变量、brief、MVU、预设角色、NPC 与界面不会跨模组残留。 |
| 3 | 技能和界面开关记录模组所有权。 | 替换只撤销模组启用项，守秘人手工启用的通用项保持不变。 |
| 4 | 导入、清理、规则固定和开关启用属于同一事务。 | 任一步失败都会恢复导入前的完整房间状态。 |
| 5 | 命令入口和管理端返回真实事务结果。 | 正文失败不会搭配 `ok: true`，半成品也不会被报告为当前模组。 |
| 6 | 包内卡片按 manifest 路径与 `kind` 解析。 | 嵌套路径、原生 JSON、酒馆 JSON / PNG 都能正确识别；多张世界卡必须明确选择。 |
| 7 | 管理端只列出可作为模组的包，并按稳定身份判断 current。 | 扩展包不会冒充模组，同名卡也不会混淆当前来源。 |
| 8 | 管理端导入与房间命令共享事务、房间回合锁和激活规则。 | 不同入口产生相同房间内容，且不会与玩家回合交错写入。 |
| 9 | 世界卡与同包独立世界书共享一个模组来源。 | 作者可把结构化卡和补充世界书组合为同一模组。 |
| 10 | 安装回执逐项说明已启用与仍需手工处理的内容。 | 提示预设、准备脚本和未激活的世界书不会被含糊地称为“可游玩”。 |
| 11 | 原始文档使用稳定 id，同名重导替换向量，删除覆盖全部同名记录。 | 检索不会召回同一路径的过期正文。 |
| 12 | 模组身份由类型、包 id、包版本和卡路径等来源信息组成。 | 同名模组仍能安全切换，管理端可以可靠匹配 current。 |
| 13 | Keeper 专长提示使用房间固定的规则系统。 | 尚未认领玩家角色时也不会装载另一套规则专长。 |
| 14 | 成功导入任一种模组都会让自动工具阶段进入 `play`。 | 世界卡房间不会持续暴露只适合准备阶段的批量工具。 |
| 15 | 玩家知识池只从开场场景开始，场景内线索随发现解锁。 | “玩家可见”不等于“玩家已经知道”，未发现线索不会提前进入玩家投影。 |
| 16 | 没有房间键的 NPC / 同伴调用使用部署默认模型。 | 独立演员调用不会在模型请求前因房间选择逻辑崩溃。 |

规则归属与事务边界记录在 [`notes/implemented/module-lifecycle-consistency.md`](notes/implemented/module-lifecycle-consistency.md)。实现入口包括 `agent/module_lifecycle.py`、`agent/kp_tools_charcard.py`、`agent/kp_tools_knowledge.py`、`module_admin.py` 与 `gateway/commands/panels.py`。
